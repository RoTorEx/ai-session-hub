# Локальные измерения — 2026-10-09

Measurements below were recorded before the rename from FleetScope to Sova.

macOS 26.6.1 arm64, iTerm2 3.7.3; живые Codex, другие терминальные задачи
продолжали работать. Это замеры этой машины, а не гарантия универсального
«идеального» интервала или нулевой нагрузки.

## Отдельные операции

Исходный установленный CLI: 5 полных сборов, медиана **847 мс**; 5 Jump на одну
текущую агентную панель, медиана **2114 мс**. CLI дополнительно собирал список
перед общим Jump, который снова делал полный сбор. Его задержка не равна одному
Apple Event. Состав живых процессов менялся по мере работы пользователя.

После изменений, `sova benchmark --samples 20 --jump SESSION_ID`:
7 агентов. Инвентарь и канал прогреты; Jump измеряет тот же общий путь, который
использует TUI, без стартовой загрузки CLI/первого полного списка.

| Операция | Медиана, мс | p95, мс | CPU FleetScope + helpers, мс/операцию | Наблюдаемый CPU iTerm2, мс/операцию |
|---|---:|---:|---:|---:|
| Нативный список процессов | 1.01 | 1.26 | 1.17 | 0.86 |
| Инвентарь с кэшем метаданных | 1.27 | 1.43 | 1.33 | 0.29 |
| Полная карта iTerm2 | 142.11 | 232.14 | 15.41 | 61.37 |
| Полный сбор без кэша | 399.47 | 454.34 | 124.23 | 131.89 |
| Контент выбранной панели | 60.35 | 86.77 | 7.73 | 35.70 |
| Точный Jump | 99.17 | 210.42 | 8.13 | 55.99 |

В CPU включены процесс FleetScope, живые прямые helper-процессы и завершённые
собственные дети. Нативное время `proc_taskinfo` переводится из Mach ticks через
системную timebase; `getrusage` учитывается в секундах. Ранние диагностические
прогоны без этого пересчёта не используются для CPU-выводов.

iTerm2 обслуживает также другие работающие панели, отрисовку и посторонние
запросы. Его столбец — весь наблюдаемый прирост за время серии; это не измерение
только дополнительных затрат FleetScope. p95 по 20 наблюдениям приблизителен;
перенос вкладки, первая загрузка API и разрешения macOS могут увеличить задержку.
После асинхронной смены окна UUID подтверждается с короткими повторными чтениями
до 250 мс; совпадение по-прежнему обязательно. После этого исправления десять
переходов между двумя окнами подтвердились: медиана 115.6 мс, максимум 196.3 мс.
Это серия API-переходов через прогретый канал; добавочная нативная проверка
идентичности занимает примерно время нативного сбора из таблицы.

## Реальные прогоны с разными интервалами

`scripts/benchmark-intervals.py` открывает только собственный TUI в PTY,
оставляет пользовательские агенты в покое и не сохраняет терминальный текст.
Цветной интерфейс (`NO_COLOR` не установлен). После трёх секунд
инициализации измеряет 15 секунд каждого профиля. Здесь
учитываются живые TUI и API-помощники; завершённые краткоживущие Git-процессы
не полностью учтены в PTY-прогонах (в отличие от таблицы отдельных операций).
Все значения
CPU — проценты **одного ядра**, без деления на число ядер компьютера.

| Процессы / контент / мета, с | CPU FleetScope + helpers | Наблюдаемый CPU iTerm2 | RSS FleetScope + helpers, MiB |
|---|---:|---:|---:|
| 1 / 1 / 1 | 2.521% | 39.058% | 75.0 |
| 2 / 2 / 2 | 1.173% | 34.625% | 74.2 |
| 5 / 5 / 5 | 0.628% | 35.763% | 73.2 |
| 2 / 5 / 30 | **0.428%** | 43.248% | 73.4 |

На этих коротких прогонах раздельный профиль уменьшил CPU-затраты живых TUI/API-помощников
примерно на 83% относительно полного секундного опроса. Изменение общего CPU
терминала не доказывает причинный эффект: фоновая работа других панелей менялась. В отдельном
15-секундном контроле без собственного TUI iTerm2 потреблял 41.555% одного ядра;
эту фоновую величину нельзя просто вычитать из несинхронных прогонов.
RSS — сумма резидентной памяти трёх процессов, не физическая уникальная память;
общие страницы могут учитываться несколько раз. Два JXA helper-процесса дают
постоянную стоимость памяти ради короткого Jump и меньшего числа запусков.

Выбрано **2 / 5 / 30 секунд**: открытия/закрытия замечаются быстро дешёвым
нативным сбором; контент выбранной панели обновляется раз в пять секунд;
расположение — раз в тридцать, при новом агенте или `r`. При выборе контент
читается после 150 мс debounce. Jump имеет отдельный прогретый канал и не ждёт
фоновой очереди; актуальное расположение разрешается по UUID при каждом Jump.
В этом 15-секундном прогоне неизменившийся экран не дал новых байтов вывода. Оптимальный интервал зависит от
содержимого scrollback, числа панелей и нагрузки терминала.

## Повторение

```sh
make bench
sova benchmark --samples 20
# Только если намерен действительно выбирать существующую панель:
sova benchmark --samples 20 --jump SESSION_ID
python3 scripts/benchmark-intervals.py --binary ~/.x-cli-sova/bin/sova --seconds 15
```

Интервальный скрипт закрывает только свои TUI/helper-процессы и временные configs.
Исправлено закрытие PTY на Darwin: родительские дескрипторы закрываются перед
ожиданием выхода session leader, чтобы сам стенд не зависал на завершении.


## Статусы всех сессий — 2026-10-09

Новая TUI читает статусы всех связанных агентов по content_seconds (5 секунд по
умолчанию), отдельно от native inventory и метаданных. Возвращается лишь хвост
видимого экрана (24 строки / 8192 символа); подробный контент остаётся выбранным.
Команда benchmark теперь включает отдельную строку `all session status`.

На восьми живых сессиях, по десять замеров: первоначальный вариант с повторными
UUID-getters дал медиану 772,75 мс и 75,27 мс CPU FleetScope + owned helpers.
После удаления лишних Apple Events получены 249,77 мс / 16,00 мс CPU; повторный
финальный прогон при другой нагрузке терминала дал 709,25 мс / 71,57 мс CPU.
Это диапазон примерно 0,32–1,43% одного ядра для дополнительного статусного
скана раз в 5 секунд, оценённый по burst-замерам. Существующие selected-content,
inventory и metadata расходы добавляются отдельно. Это не повтор прежнего
15-секундного steady-state PTY-профиля; нагрузка и число агентов изменились.
Измеренная iTerm CPU включает другие сессии и не приписывается FleetScope целиком.
Уменьшать интервал для всех панелей до 1 секунды на основании этих данных нельзя;
5 секунд оставлены как компромисс. При большой нагрузке content_seconds можно
увеличить, учитывая более редкое наблюдение завершений/открытий.
